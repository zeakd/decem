# Gate C: boundary hunt

Random inputs essentially never land on a rounding tie. At 34 digits the chance of an
exact value falling on a half-ulp boundary is negligible, so passing gate A across
thousands of cases demonstrates very little about rounding.

Boundaries are not encountered. They are constructed.

```
div    q = a (p+1)-digit integer ending in 5, so a = q*b puts a/b exactly on the tie
       at p digits, and a = q*b -/+ 1 puts it just below or just above

sqrt   the same shape with x = s^2
cbrt   the same shape with x = s^3
```

At a tie the seven rounding modes disagree with each other, which is exactly where an
implementation can be wrong while looking right everywhere else.

## Transcendental boundaries are constructible too

This was once written down as impossible, on the grounds that `exp` and `ln` are not
algebraic. That was wrong. Their inverses do the construction:

```
y = a (p+1)-digit integer ending in 5, the value we want to be a tie at p digits
x = ln(y)     makes exp(x)   land near y
x = exp(y)    makes ln(x)    land near y
x = 10**y     makes log10(x) land near y
x = asin(y)   makes sin(x)   land near y, and acos and atan the same way
```

Trigonometry was written here as out of reach, on the grounds that reduction by pi
defeats the construction. That was the second time this page called something impossible
and was wrong. An inverse sine lands inside `(-pi/2, pi/2)`, where there is nothing to
reduce, so the tie is reached exactly as it is for `exp`. All 1,890 trigonometric cases
passed on the first run.

`x` has to be truncated to a finite number of digits, so the result is not exactly on the
tie but very near it. That turns out to be better: when defects were injected, the sticky
bit failure showed up only on the `above` side, never on the tie itself.

Generated by `gen-transcendental.py` using MPFR, 2,835 cases.

**That axis found a real defect on its first run.** Six `exp` cases disagreed with the
oracle, and working through the series by hand showed denary was right: the deviation sat
at the 101st digit while the oracle was computing to 97. The oracle now raises its own
precision until the answer stops moving.

## Does this gate actually catch anything?

A gate that has never failed is a gate of unknown strength, so three defects were injected
deliberately:

| Injected defect | Gate A | Gate C | Where it failed |
|---|---:|---:|---|
| removed the sticky bit in `div` | 2 | **48** | `above` only |
| `half-even` replaced by `half-up` | **0** | **45** | `tie` only |
| removed `sqrt` guard digits | 42 | **24** | `above` only |

The second row is the reason this gate exists. Gate A ran all 2,631 cases and caught
nothing at all, because none of them is a tie.

The failure position also names the kind of defect: `tie` alone points at the mode
decision, `above` alone at the sticky bit or the guard digits.

## Running it

```sh
node    test/boundary/gen-boundary.mjs           # algebraic cases, deterministic
python3 test/boundary/gen-transcendental.py      # inverse-function cases, needs MPFR
python3 test/boundary/oracle-boundary.py         # answers, reusing gate A's oracle
node    test/boundary/compare.mjs                # run the gate
```

## The second axis found a defect too

`log10` was exempt from this gate, on the recorded grounds that `ln` exercises the same
path. It does not. `log10` divides by `ln(10)`, and that constant's error enters the
result in proportion to the result: `log10` of `10^100` is a hundred, so the constant is
effectively used a hundred times. The allowance for it was a written down figure that did
not grow, so fifteen cases just below `10^10` rounded the wrong way at a tie.

The constants now report their own error along with their value, which removed the same
written down figure from `exp` and `ln` as well. Neither of those had failed, but both
had the same understatement waiting at a larger width.

## What this gate does not cover

- **`scale` precision for the transcendental operations.** Constructed ties on the scale
  axis cover `quantize`; the inverse-function axis is built on `digits`.
